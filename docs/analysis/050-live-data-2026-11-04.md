Findings
A. Critical — money-safety
1. Protective-repair path cancelled a mid-fill exit, then gave up with a stale qty.
The old reconcile cancelled the in-flight market sell to free shares for a protective stop (truncating the exit at 14/21), then retried the stop with the original 21 instead of the remaining 7 — rejected twice (insufficient qty). After that, every pass compared sold (14) >= qty (7) and concluded "fills already cover" — comparing past fills against remaining size instead of original size. No stop for ~6h; the position rode 1.5h of live session naked and went unmonitored during the dead window.
→ Fixed in the 043 series (the code comments literally cite "KO, 4 Nov"): in-flight market sells deferred, qty from qty_available, cover check vs original size, pending_exit persisted (f606b9d).

2. apply_auto_resolution resolves by quiet time, not by condition cleared — still live.
Events 537/538 (protective_stop_failed) resolved auto at 16:46:34 purely because the error hadn't recurred for 60 minutes — it hadn't recurred because the buggy skip was logging at INFO. Readiness "errors in log" went green while a position sat unprotected for another 5 hours. Auto-resolution should re-verify the condition (position actually has a working stop) before clearing a protective_stop* event. service.py:298-332

3. ~1-hour silent outage mid-session, no heartbeat configured.
PID 3289447's last log is 18:46:35 (the task.failed for the shadow crash — likely coincidence, not cause: it was caught). No shutdown lines → SIGKILL/OOM/manual kill. Nothing ran for 61 minutes. The spec calls the heartbeat "the only alert that still works when the server itself is down" (/home/marc/Repositories/stock-trading-agent/docs/SPEC.md §Heartbeat) — live config has "heartbeat_url": "". Unclean-stop detection, quick_check, and the unclean banner did work on restart (dismissed 19:49). Gap: no external dead-man's switch and no supervisor auto-restart.

4. Shadow runner crashed on every Nov-4 cycle.
UnboundLocalError: gate_detail at runner.py:1636 killed shadows-cycle-330/334/338/342 — the EP candidate pass aborted mid-way each cycle (rows written before the crash survive; anything after is lost). Fixed in 9fd6b3b, committed 21:57 UTC that evening.

B. Model / review pipeline
5. gpt-6.1-sol broke the daily briefing — twice.
Settings v24 (4 Nov 14:03) switched reviews.models.briefing/weekly to gpt-6.1-sol. OpenAI rejects temperature: 0.2 for it → briefing fell back to template on 5 Nov and 6 Nov (llm_call api_error 400). Code fix (_temperature_kwargs + supports_temperature) landed 5 Nov, but the flag only reached live settings in v26 (6 Nov 14:23) — so it failed a second day. Weekly review (7 Nov 09:00) now succeeds. Lesson: model-capability flags live in config but model assignment is also config — nothing validates the pair at save time.

6. Verdict number-check rejected all 15 fallback verdicts (4 Nov 06:12).
number_check_failed on every fallback verdict (gpt-4.1-mini); the affected verdicts stayed draft, and the confirm backlog grew 42 → 78 over the two days. Either the checker demands numbers the fallback can't produce, or it counts wrong — worth a look at the check vs. what a template verdict contains.

7. Model can't see broker-side protection state.
Decision 4204's position snapshot shows "stop": 94.22 — the stored stop — while no working stop existed at Alpaca. Defensible (repair is code-level), but on 4 Nov the model "held" a position whose actual protection had been broken for hours.

C. Config / operational
8. missing_stop — the top critical event — was browser-only until v26. new_error had email but missing_stop had only ["browser"] on 4–5 Nov. You only saw it in the UI. Fixed in v26 (6 Nov).

9. Offsite backups & restore test not working. server-status.json: offsite: null, restore_test.ok=false ("no backup password or storage credentials stored") since 1 Nov. Local daily backups fine.

10. Stale leftovers: orders.submitted_at NULL on 47/49 orders (only new-code rows populate it); pdt_max_day_trades still in live settings despite the retired PDT rule; day_trades table empty as expected.

D. Verified working as designed (no action)
Shock brake: blocked all 11 enter decisions on 5 Nov — SPY genuinely fell >1.5%/h repeatedly (765.5 → ~733, −4%). Correct.
price_stale/price_suspect blocks: bars were fresh; IEX quote timestamps stale for quiet symbols — conservative direction, fine.
Bracket structure intact on entries (entry+target+stop legs); whole shares; Decimal-exact P&L; paper-only (sa-salocal client IDs, MODE=paper); log scrubber redacts tokens; request gate shows only trivial 404s; zero sign-in attempts under SA_AUTH=off on 127.0.0.1 — all consistent with the hard rules.
after_exit_status=pending on closed positions is correct (5-session window still open).
Recommended follow-ups
Make auto-resolution state-verifying for protective_stop*/reconciliation events (finding 2).
Set ops.heartbeat_url (finding 3) — it's a config change, no code.
Validate model capability flags when a model is assigned in Settings (finding 5).
Investigate the verdict number-check on fallback/template verdicts (finding 6).
Consider logging the cause of process death — e.g., persist last-alive heartbeat so the next start can report "killed externally vs crashed" (finding 3).

## Verdict number check (item 050 step 9)

Why 15 of 15 model verdicts failed `number_check_failed` on 4 Nov 06:12–06:13
(`llm_calls` 2434–2468, `verdict.v2`, gpt-4.1-mini):

- The stored rejection detail (`error_message`) lists the rejected tokens:
  `1`, `1, 1`, `1, 1, 1` and once `1, 7`. Almost every model text contains
  "1-hour trend" — the check at the time scanned "1" inside "1-hour" as a
  bare number, and the verdict facts hold no number that rounds to 1
  (prices, percentages, counts are all different values). The "7" is
  "ATR level L7" in call 2459.
- Re-running the current `bad_numbers` on the stored `sent_input` facts
  and raw texts: every call passes except 2466, whose "price fell 4%
  afterwards" invents a number no fact holds — a correct rejection.
- The fix already exists: `bc81993` "number check: mask identifiers, not
  just dates and times" (4 Nov 08:07, two hours after the calls) masks
  identifier-shaped tokens like `1-hour` and `L7` before scanning.

Conclusion: the 15 failures were a masking bug in the number check, not a
prompt or template defect; it was fixed the same morning by `bc81993`.
No code change in this item — the current check rejects the model text
only when it should (2466). The confirm backlog (42 → 78) is the draft
queue from finding 6, not new work from this check.
